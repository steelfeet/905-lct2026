## Прогон 2 — 50 параллельных пользователей

Смешанный профиль по 5 ролям (`manager`, `supervisor`, `university`,
`student`, `parent`), логин через OIDC-stub, переходы по разделам, смена
фазы проекта через `POST /index.php?action=move_phase`.

```
scenario: concurrent_users_50   ramping-vus 0→25→50→50→0 (3 мин 30 с)

checks_total.......: 18 421   ✓ 99.87%
http_reqs..........: 14 302   68.1/s
iterations.........:  3 214
vus_max............:     50   (достигнуто, held 2m)
http_req_failed....:  0.13%   (19 из 14 302 — таймауты на холодном старте)

http_req_duration:
  avg..............: 312 ms
  med..............: 248 ms
  p(90)............: 561 ms
  p(95)............: 683 ms   ✓ порог 1000
  p(99)............: 902 ms
  max..............: 1 487 ms

по эндпоинтам (p95):
  login.............:  211 ms   ✓ порог 1000
  main_page.........:  384 ms   ✓ порог 1000
  dashboard.........:  627 ms   ✓ порог 1000
  workflow_page.....:  452 ms   ✓ порог 1000
  move_phase........:  338 ms   ✓ порог 1000
    └ no `<!DOCTYPE`..:  100%  ✓  (проверка «без перезагрузки»)
    └ `ok: true`......:  99.9%

login_failures.....:  0.02%   ✓ порог 1%
```

### Наблюдения

- 19 ошибок — таймауты на первых 30 секундах, пока php-fpm прогревал пул.
  После прогрева `http_req_failed = 0`. В прод-окружении лечится
  `pm.start_servers` / `pm.min_spare_servers`.
- Самый тяжёлый эндпоинт — дашборд руководителя: inline-генерация
  12 месяцев × 8 вузов × 14 фаз. `p95 = 627 ms` — укладывается в 1 с, но с
  небольшим запасом. Кандидат на вынос агрегации в Redis.
- `move_phase` стабильно < 400 ms, ответ — только JSON, HTML в тело не
  попадает (подтверждает NFR п.2 — без полной перезагрузки).

**Итог: PASS** по всем порогам.

## Прогон 3 — 10 параллельных отчётов

10 VU в течение 2 минут бьют по дашборду с разными периодами (3 / 6 / 12 мес).
В прототипе отчёт рендерится через тот же pipeline агрегации, что и
`/reports` — нагрузка репрезентативна.

```
scenario: parallel_reports_10   constant-vus 10 (2 мин)

checks_total.......: 1 782     ✓ 100%
http_reqs..........:   591     4.9/s
iterations.........:   591
vus_max............:    10     (constant)

http_req_duration:
  avg..............: 1 024 ms
  med..............:   877 ms
  p(90)............: 1 618 ms
  p(95)............: 1 924 ms   ✓ порог 3000
  p(99)............: 2 401 ms
  max..............: 2 738 ms

по периодам (p95):
  period=3........:   986 ms
  period=6........: 1 512 ms
  period=12.......: 2 108 ms   ← самый тяжёлый

http_req_failed....:  0.00%   ✓ порог 1%
```

### Наблюдения

- 12-месячный отчёт в 2.1× тяжелее 3-месячного — линейно по объёму
  агрегируемых данных. При росте числа вузов/фаз за пределы пилота
  (сейчас 10 × 15) потребуется предварительная материализация
  месячных срезов.
- Параллельные отчёты не мешают друг другу: при 10 VU p95 держится
  в ~2 с, что даёт запас к порогу 3 с.
- Ошибок нет — блокировок БД на чтение в текущей схеме не возникает.

**Итог: PASS** по всем порогам.

## Вывод

Прототип держит заявленные в ТЗ 50 параллельных пользователей и 10
параллельных отчётов на эталонном окружении с запасом. Узкие места для
прода:

- дашборд руководителя (ближе всех к 1 с на общем профиле);
- 12-месячный отчёт (2.1 с при p95 — до порога 3 с осталось мало).

Для прода рекомендуется: вынести агрегаты дашборда в Redis с TTL 5 минут,
материализовать месячные срезы, прогнать smoke против реального Keycloak
(ожидаемый прирост p95 на логине +30–50 мс).

## Ограничения прогонов

- Значения получены на keycloak-stub и синтетическом сиде.
- `/reports` как отдельный endpoint в прототипе не реализован — нагрузка на
  отчёты измерена через дашборд с фильтрами (тот же pipeline агрегации).
- Файловые вложения и экспорт XLS/PDF/XLSX в прототипе не реализованы —
  профиль для них не снят.
- Перед защитой проекта на реальных данных перезапустить `k6-basic.js` и
  `k6-reports.js` на прод-подобном окружении и обновить таблицу.
